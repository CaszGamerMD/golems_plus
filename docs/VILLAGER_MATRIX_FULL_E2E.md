### Current blockers (first complete-file import)

Original importer + block resolver: 107 unsupported palette variants.
After resolving inventory-backed block entities, redstone dust, and correctly
counted bed heads, 17 variants (759 cells) remained. Flowing water 1–6 is
now recognized as **17 non-item natural propagation positions**: the Builder
only completes them after the actual fluid state appears, never by writing
a synthetic water-level block. As of the latest full-file import, **11
unsupported generated-state variants affect 742 schematic cells**:

| Category | Cells | Requirement |
| --- | ---: | --- |
| Extended piston / sticky piston | 370 | Place retracted body, then power through real vanilla redstone |
| Piston heads | 370 | Generated by piston extension, NEVER an inventory item |
| Soul fire | 2 | Real ignition on soul sand with safe player/tool interaction |
| Flowing water levels 1–6 | 17 | Now modeled as source-dependent no-item state verification |

**Important: 131 of 370 extended pistons have their same-facing piston
heads ONE CELL BEHIND the base instead of in front.** The other 239 are
forward-aligned. `BuilderPistonAssemblyAudit.inspect` checks each pair's
local XYZ, direction, head type, and the would-be forward cell. These 131
pairs cannot be created through normal piston extension as encoded; they
might reflect a transient redstone snapshot. The user source is preserved
unchanged, never silently "fixed" by flipping a piston or head.

**Do not remove these cells or fake them with direct world-state writes.**
Full-build acceptance stays blocked until the actual saved geometry and
remaining redstone / ignition mechanics can be reproduced.

### Partial physical diagnostics using the exact same user file

`builder-villager-matrix-lower-physical.yml` runs
`BuilderVillagerMatrixLowerLayersGameTest` on the **original full checksum
verified file** using the NORMAL bottom-up full-job work order. It measures
the first 107 genuine non-air cells at source Y=0–3 while four real Builders
use a paid chest/scaffold supply. It does not change the imported schematic,
skip the upper layers, or reverse construction order. It is useful for
navigation, work-stances, floating starts, and regression timing.

A **107/107** lower-layer result NEVER satisfies, replaces, or bypasses
the required **15,376/15,376** full-build acceptance.

Lower-layer four-Builder runs have reached approximately **50–52/107**
source cells, then stalled at source-local `(15,1,24)`:
`minecraft:powered_rail[powered=true,shape=ascending_west,waterlogged=true]`.
The original source requires an `iron_trapdoor` at its raised end
`(14,2,24)`, a flat powered rail beneath that at `(14,1,24)`,
and a redstone block at `(13,0,24)`.

**The rail physics was measured in three separate bootstrapped vanilla
GameTests** under `BuilderMatrixRailPhysicsGameTest`:

1. In an isolated **idealized** test with a temporary raised-end rail
   supported by **stone**, an ascending rail **keeps its slope** when
   the jig is removed; without a redstone circuit it loses only
   `powered=true`. This exposed an earlier incorrect diagnosis.
2. In the **actual saved Matrix neighborhood**, the real redstone
   block powers all three rails, but the target becomes
   `powered=true,shape=east_west`. The raised jig **cannot survive**
   on the flat rail at `(14,1,24)`.
3. Even when a temporary **stone support** is used to create the incline
   before restoring the exact neighboring rail, the target rail
   **breaks to air** on restoration. There is currently no verified,
   normal-Minecraft construction sequence for the exact saved states.

A separate read-only `BuilderRailAssemblyAudit` finds **371 ascending
rails**, **234 raised-end/rail-footing conflict patterns** in the exact
full source. This is a candidate-problem count, **not a claim that all
234 have been individually physically tested**. The Planner logs the
locations and exposes them on Builder inspection; it does not discard
blocks, overwrite the imported hologram, or invent powered states.

The Builder now distinguishes a true rail-shape mismatch from redstone
power and waterlogging. An already paid and correctly sloped rail is
**not cleared or rebuilt** just because the redstone or water state is
not yet physically correct. Full completion remains strict, including
the uncorrected rail conflict.

### Block-entity caveat

The original file includes 40 block-entity NBT records (e.g. container
inventories). The current production `LitematicFileReader` intentionally
does not restore block-entity NBT. The physical GameTest covers **block-state
geometry**; a separate block-entity content-restore feature/test is needed
before anyone claims a fully functional redstone machine clone.
